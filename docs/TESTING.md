# Автоматические тесты движка

Автотесты защищают код движка от регрессий и не заменяют встроенную проверку
конкретной новеллы в статистике и графах. Автор истории продолжает пользоваться
инструментами внутри интерфейса, а разработчик движка и Codex запускают тесты
после изменения исходного кода.

## Требования

- Node.js 22 или новее;
- локальная копия Git-репозитория;
- установка npm-пакетов не требуется;
- подключение к сети не требуется.

Тесты и Node.js не входят в пользовательский runtime движка и не нужны для
запуска готовой новеллы.

## Запуск

Полная проверка:

```powershell
node --test
```

Все проверки `story-loader.js`:

```powershell
npm run test:parser
```

Метаданные и диагностика ошибок:

```powershell
npm run test:meta
```

Команды сцен, переходы, условия и меню:

```powershell
npm run test:scenes
```

Переменные, синтаксис и runtime-вычисление выражений:

```powershell
npm run test:variables
```

Объявления и параметры синтетических медиа:

```powershell
npm run test:assets
```

Команды `bg360marks`, `walk360` и `goto360`:

```powershell
npm run test:360
```

Счётчики встроенной статистики загрузчика:

```powershell
npm run test:stats
```

Протокол мини-игр, состав релиза и ссылки документации:

```powershell
npm run test:protocol
npm run test:release
npm run test:links
```

В PowerShell с запрещёнными сценариями `npm.ps1` используйте `node --test` для полного набора
или команды `node --test tests/<имя>.test.mjs` для отдельных файлов.

Успешный запуск завершается кодом `0`. Любой проваленный тест возвращает
ненулевой код, поэтому GitHub Actions и Codex могут автоматически остановить
проверку и показать имя нарушенного контракта.

## Что проверяется сейчас

- заголовок `title` с двойными, одинарными кавычками и без кавычек;
- значения meta по умолчанию, преобразование всех поддерживаемых параметров и ошибки режимов;
- совместимость устаревших секций и старого формата `menu`;
- полный разбор поставляемого `story-example.js`;
- основные команды сцен, диалоги, фон, персонажи, музыка, видео и игры;
- все виды переходов, вложенные `choice` и `if / elif / else`, старый и новый форматы `menu`;
- параметры оформления меню, незакрытые блоки и недопустимые управляющие слова;
- типы и имена переменных, синтаксис выражений и настоящий runtime-evaluator из `engine.js`;
- арифметика, сравнения, строки, логические операторы и запрет опасных идентификаторов;
- регистрация, алиасы, legacy-формат и визуальные параметры синтетических медиа;
- диапазоны громкости, фокуса, масштаба, 360-FOV и обязательность `file`;
- команды `bg360marks`, `walk360`, `goto360`, photo-метки и их диагностические ошибки;
- формат диагностических ошибок и итоговые счётчики встроенной статистики загрузчика;
- создание `gameInit`, защита его служебных полей и распознавание `gameResult` на искусственных объектах;
- нормализация числового, отсутствующего и некорректного результата мини-игры;
- существование обязательных runtime-файлов, их включение в релиз и отсутствие developer-тестов в ZIP;
- существование относительных ссылок в отслеживаемой Markdown-документации.

Тест полного разбора читает текст `story-example.js`, но не открывает указанные в нём файлы ассетов.
Отдельные тесты ассетов используют только вымышленные пути внутри синтетических сценариев, а тесты
протокола — искусственные объекты сообщений. Игнорируемый пользовательский `story.js`, реальные
мини-игры и локальные неотслеживаемые ассеты не участвуют в проверке.

## Правила расширения

- Каждое исправление ошибки парсера сопровождается регрессионным тестом.
- Ожидаемый результат меняется только вместе с осознанным изменением
  спецификации или обратной совместимости.
- Fixtures должны быть небольшими и проверять один понятный контракт.
- Тесты не должны обращаться к сети или зависеть от случайных локальных файлов.
- Перед завершением изменения движка выполняется полный `node --test`.

За пределами этого набора остаются только проверки, которым действительно нужен браузер: визуальная
компоновка, DOM-события, автосохранение в `localStorage`, реальный iframe и загрузка файлов по URL.
Их можно добавить отдельным e2e-набором. Проверка файлов конкретной демо-новеллы также намеренно
не входит в developer-тесты движка.

## GitHub Actions

Workflow `.github/workflows/tests.yml` запускает полный набор:

- после push в `main`;
- для pull request;
- вручную через `workflow_dispatch`.

Release workflow повторяет тесты перед сборкой ZIP. Провал проверки не позволяет
собрать и загрузить релизные архивы.

### Безопасная ручная проверка ZIP

Workflow `Build ZIP for Release` можно запустить во вкладке **Actions** без
создания релиза и без изменения GitHub Pages:

1. Нажмите **Run workflow**.
2. В поле версии укажите временное имя, например `test-build`.
3. Оставьте `upload_to_release` и `deploy_pages` выключенными — это их безопасные значения по умолчанию.
4. После успешного завершения скачайте `release-zips-<run id>` в разделе **Artifacts** запуска.

Внутри artifact находятся полный и update-ZIP. Workflow проверяет целостность
обоих архивов, наличие runtime и пользовательских инструментов, отсутствие
developer-файлов, а также отсутствие ассетов и корневого сценария в
update-архиве. Artifact хранится семь дней.

Включайте `upload_to_release` или `deploy_pages` только для настоящей
публикации: эти параметры соответственно изменяют GitHub Release и демо на
GitHub Pages. При событии публикации релиза оба действия по-прежнему
выполняются автоматически.

Каталог `tests/`, `package.json` и этот документ нужны только разработчику и GitHub Actions.
Release workflow не копирует их в пользовательские ZIP-архивы.
