# Загрузка story.js и story360.js и сохранённый Worker-режим

Статус: действующее архитектурное решение.

По умолчанию авторские файлы выполняются обычными `<script>` в основном окне.
Worker-загрузчик сохранён для возможного возврата изоляции; этот документ
описывает оба способа и причину выбора совместимого автономного запуска.

## Причина решения

`story.js` удобен для ручного редактирования: сценарий остаётся свободным
многострочным текстом внутри `window.STORY_TEXT`. `story360.js` создаётся
редактором и задаёт JSON-подобный объект `window.STORY360`. Оба файла должны
автоматически загружаться после F5 при запуске через `file://`.

Прямое подключение через `<script>` выполняло весь пользовательский код с
правами основной страницы. Пассивные TXT/JSON нельзя надёжно прочитать по пути
через `file://`, а читаемая CSS-обёртка заметно ухудшает ручное редактирование
основного сценария.

## Сбой локальной загрузки и решение от 2026-09-02

При открытии проекта через `file://` установленный Chrome показывал чёрный экран
с сообщением, что `story-example.js` отсутствует или содержит ошибку. При этом
основной `story.js` и резервный пример существовали и содержали корректные данные.
В консоли появлялись сообщения:

```text
[Bootstrap] story.js не найден, используется story-example.js
Не удалось принять данные сценария: Неизвестная ошибка sandbox-загрузчика.
'file:' URLs are treated as unique security origins.
```

Изолированная проверка уточнила место отказа: создание Blob Worker проходило,
но вызов `importScripts(file:///.../story.js)` внутри него завершался
`NetworkError`. Старый загрузчик преобразовывал эту ошибку в статус `missing`,
из-за чего отказ в доступе ошибочно выглядел как отсутствие файла. Попытка
загрузить `story-example.js` тем же способом тоже завершалась отказом.
Это ограничение конкретного пути загрузки, а не общий запрет локального JavaScript:
обычные скрипты страницы продолжали подключаться.

Зафиксированные результаты без отключения защиты браузеров:

| Проверка | Результат |
| --- | --- |
| Google Chrome 152.0.7977.64, Blob Worker → `importScripts(file://...)` | Отказ `NetworkError` |
| Chromium 151.0.7922.34, тот же импорт | Успех в headless-shell и в полном Chromium |
| Chrome 152, обычные `<script>` с авторскими файлами | Успех, включая F5 |
| Firefox 155 со строгой политикой локальных origin, обычные `<script>` | Успех, включая F5 |

Связь с обновлением браузера вероятна, но сравнивались разные сборки Chrome и
Chromium. Конкретный upstream-коммит, намеренное ужесточение или ошибка браузера
не установлены. Нельзя записывать предполагаемую причину как доказанный факт.

Сбой проявился после исправлений CSS-панорам Firefox и очистки пустого BGM, но
отказ происходил ещё при загрузке сценария, до запуска этих контроллеров.
Последние исправления панорам и аудио не меняли `index.html` и Worker-загрузчик;
их откат не был выбран решением этой проблемы.

Пользователь исключил сервер и отказался от дополнительной упаковки после
редактирования сценария. Принято решение вернуть обычное подключение всех трёх
файлов: `story.js`, резервного `story-example.js` и необязательного `story360.js`.
Worker-защиту решено сохранить вместе с тестами для возможного возврата.
Выбор относится к запуску и через `file://`, и через HTTP(S); автоматического
выбора режима по протоколу нет.

### Проверенные и отложенные варианты

В прототипах Chrome 152 принимал исходный JS через `data:` URL внутри прежнего
Worker-загрузчика. Проверены настоящие `story.js` и `story360.js`; сценарий
по-прежнему не получал DOM и заблокированные сетевые API. Но сначала нужно
разрешённым способом получить исходный текст — сам `data:` URL этого не решает.

| Вариант | Наблюдение и причина отказа от внедрения |
| --- | --- |
| Выбор файлов через File API, затем передача текста в Worker через `data:` | Работал; требует ручного выбора вместо автоматического чтения после F5 |
| Генерируемый пакет с текстами JS в инертном CSS, затем `data:` в Worker | Работал; после правок нужно пересоздавать пакет, что пользователь признал неудобным |
| Инертные данные внутри HTML, затем `data:` в Worker | Работали, в том числе после F5; для обновления сценария требуется пересборка HTML |
| `fetch(file://...)` или чтение JS как текстового документа в iframe | В проверках не дали доступ к тексту; не заменяют отсутствующий транспорт |
| Импорт в Worker через Blob URL, созданный родительской страницей | В проверенном Chrome 152 также завершался отказом; замена схемы на `blob:` не доказала совместимость |

Это результаты прототипов, а не готовая спецификация пакета данных. Упаковщик,
новый формат сценария и дополнительный шаг сборки в продукт не добавлены.

## Действующая схема

`index.html` задаёт `STORY_SCRIPT_LOAD_MODE = "direct"`. Загрузчик последовательно
подключает `story.js` (либо `story-example.js`) и необязательный `story360.js`
обычными `<script>`, затем проверяет экспортированные данные и запускает движок.
F5 читает актуальные исходные файлы без упаковки, ручного выбора и сервера.

Такой режим выбран после воспроизведения отказа `importScripts(file://...)` из
Blob Worker в установленном Chrome 152.0.7977.64. В Chromium 151.0.7922.34 тот же
путь работал. Конкретное изменение Chromium или причина регрессии не установлены;
полагаться на прежнюю доступность Worker-импорта локальных файлов нельзя.

Исполняемый авторский JS теперь доверен наравне с кодом страницы: он имеет доступ
к DOM и доступным ей API. Проверка результата не изолирует уже выполненный код.
Общий валидатор сохраняет лимит текста 8 МиБ и прежние структурные ограничения
карты: версия 1, JSON-подобная копия, нулевые прототипы, квоты и отказ опасным ключам.
Ошибки синтаксиса и выполнения учитываются отдельно от `script.onload`, включая
исключение после присваивания данных. Частично созданный экспорт очищается.

Константа со значением `"worker"` выбирает сохранённую ветку изоляции, но сама
по себе не устраняет отказ локального импорта в Chrome 152. Перед сменой режима
по умолчанию нужно выполнить условия раздела о возврате защиты ниже.
Режим не выбирается URL-параметром и не меняется автоматически после ошибки:
неудачная Worker-загрузка никогда не приводит к выполнению файла в странице.
API обоих режимов находится в `engine/story-sandbox-loader.js`; существующие
`loadStoryText`/`loadStory360` сохраняют Worker-контракт, а методы с суффиксом
`Direct` подключают обычный script. Оба режима используют одну фабрику валидаторов.

## Сохранённая схема Worker

`engine/story-sandbox-loader.js` создаёт отдельный Blob Web Worker для каждого
файла. Worker заранее создаёт отдельный объект `window`, сохраняет доверенную
ссылку на `importScripts`, блокирует обычные сетевые, вложенные Worker и
браузерные storage API, а затем импортирует ровно запрошенный локальный файл.

Результат возвращается по приватному `MessageChannel`, который хранится в
замыкании bootstrap-кода и недоступен пользовательскому скрипту:

- из `story.js` принимается только строка `window.STORY_TEXT`;
- из `story360.js` принимается только объект `window.STORY360`;
- функции, специальные прототипы, циклы, опасные ключи и чрезмерно большие
  структуры `STORY360` отклоняются;
- после результата или таймаута Worker принудительно завершается.

Основная страница не слушает обычный `worker.postMessage`, поэтому
пользовательский файл не может подменить служебный ответ без приватного порта.

## Отсутствующие и повреждённые файлы

- если `story.js` недоступен, тем же способом загружается `story-example.js`;
- если найденный `story.js` не создал строку или завершился ошибкой, пример не
  подставляется и показывается ошибка проекта;
- отсутствие `story360.js` является штатным и не мешает обычным сценам;
- повреждённый `story360.js` отключает только карту пространств и оставляет
  диагностическое предупреждение.

Событие `script.onerror`, как и `NetworkError` Worker-импорта, не различает
отсутствие файла и отказ браузера в доступе. Поэтому предупреждение говорит
«недоступен». Таймаут обычного script ограничивает только ожидание загрузки;
остановить бесконечный цикл в основном потоке он не способен.

## Почему не sandbox-iframe

В Chromium opaque-origin iframe с `sandbox="allow-scripts"` не может загрузить
соседний локальный `<script>` через `file://`: браузер сообщает
`Not allowed to load local resource`. Добавление `allow-same-origin` вернуло бы
загрузку, но создало бы опасное сочетание прав и зависело бы от различающейся
между браузерами модели origin локальных файлов.

Blob Worker сохраняет отдельный поток и в прежнем Chromium позволял вызвать
`importScripts(file:///.../story.js)`, поэтому первоначально был выбран вместо
iframe. После отказа этого пути в Chrome 152 он остаётся сохранённым режимом.

## Граница защиты

Только Worker-режим предотвращает прямой доступ сценария к DOM, функциям и `localStorage`
основного окна и позволяет остановить бесконечный цикл по внешнему таймауту. Он
не превращает JS в пассивный формат и не является границей против уязвимостей
самого браузера. Динамические возможности JavaScript требуют считать Worker
изоляцией с уменьшенными правами, а не исполнением доказанно безопасных данных.

Корневой `story360.js` не следует путать со старыми пакетами изображений
`*-360.js`. Движок отвергает такие пути и принимает автономные панорамные
изображения только в декларативных `*-360.css`; детали описаны в
`360-panorama-packages.md`.

## Условия возврата защитного режима

1. Подтвердить разрешённый способ загрузки исходного JS в Worker в актуальном
   установленном Chrome и Firefox. Либо браузеры снова поддерживают прежний
   импорт, либо найден другой транспорт. Успех создания Worker и работа через
   HTTP не доказывают возможность прочитать соседний файл через `file://`.
2. Сохранить обязательный авторский процесс: редактирование исходных JS,
   сохранение, F5, без сервера, упаковки и повторного выбора файлов. Если новый
   транспорт требует изменить этот процесс, сначала согласовать это с
   пользователем; ранее упаковка была явно отклонена.
3. Выполнять авторский JS только внутри Worker. Загрузка его обычным script в
   страницу с последующей передачей результата в Worker не восстанавливает
   защиту: побочные эффекты уже произошли. Нельзя маскировать несовместимость
   отключением браузерной защиты, послаблением sandbox или прямым fallback.
4. Сохранить приватный `MessageChannel`, блокировку побочных API до выполнения
   файла, таймаут с `terminate()`, закрытие портов и отзыв Blob URL. Валидаторы
   должны работать внутри Worker до structured clone, использовать сохранённые
   встроенные функции и прежние квоты; основная страница восстанавливает нулевые
   прототипы уже проверенной карты. Фабрика `createStoryDataValidators` и
   `workerBootstrap` должны сериализоваться вместе без зависимостей от страницы.
5. Повторить проверки корректного, отсутствующего и повреждённого основного
   сценария, резервного примера и необязательной карты. Не считать любую
   `NetworkError` доказательством отсутствия файла: если различить причины
   невозможно, диагностика должна сообщать о недоступности, сохраняя источник.
   Ошибка выполнения или валидации существующего сценария не допускает демо.
6. Проверить реальный `file://` в установленных браузерах с записью их версий,
   а также HTTP(S), F5 после изменения обоих файлов, переходы, перезапуск,
   ошибки и очистку ресурсов. Bundled Chromium одной версии и HTTP-тесты
   недостаточны для решения о включении защиты по умолчанию.
7. Только после этих проверок заменить `STORY_SCRIPT_LOAD_MODE` на `"worker"`,
   обновить описание действующего режима и модель угроз. При выпуске обновления
   пересоздать `release-manifest.json` штатным релизным процессом.

Для Playwright Test строгая политика Firefox задаётся именно через
`use.launchOptions.firefoxUserPrefs`:

```javascript
test.use({
  launchOptions: {
    firefoxUserPrefs: { "security.fileuri.strict_origin_policy": true }
  }
});
```

При прямом `firefox.launch()` параметр `firefoxUserPrefs` передают в аргументе
запуска. Для установленного Firefox с `channel: "moz-firefox"` это особенно
важно: настройки автоматизации по умолчанию ослабляют локальный доступ.
Поле `firefoxUserPrefs` непосредственно внутри `test.use` не задаёт эти prefs.
Заявлять совместимость по такому ошибочно настроенному тесту нельзя.

После возврата обычного подключения прошли 390 Node-тестов, полный E2E-набор
Chromium/Firefox (172 успешных, 2 пропущенных из-за наличия авторского `story.js`),
20 отдельных проверок `file://` в установленном Chrome 152 и Firefox 155 и запуск
самой пользовательской копии в обоих браузерах. Сценарий отсутствующего файла
дополнительно проверен в изолированных копиях без зависимости от рабочего дерева.
Сохранённые Worker-тесты подтверждают защитные свойства под HTTP и в тестовом
окружении; они не подтверждают исправление исходного Worker-импорта `file://`.

## Проверки при изменении

Нужно проверять:

1. обычный script под HTTP и `file://`, изменения после F5 и запуск без Worker;
2. fallback на `story-example.js` при недоступности `story.js`, но не при ошибке его выполнения или данных;
3. optional-отсутствие и структурную проверку `story360.js`;
4. сохранённый Worker-режим: изоляцию, завершение и отсутствие прямого fallback;
5. Chromium, установленный Chrome и Firefox со строгой политикой `file://`.

Проверки закреплены в
[story-sandbox-loader.test.mjs](../tests/story-sandbox-loader.test.mjs),
[bootstrap-runtime.test.mjs](../tests/bootstrap-runtime.test.mjs),
[engine.spec.mjs](../tests/e2e/engine.spec.mjs) и
[local-story-bootstrap.spec.mjs](../tests/e2e/local-story-bootstrap.spec.mjs).
