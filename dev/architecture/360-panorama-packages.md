# Автономная загрузка 360-панорам

Статус: действующее архитектурное решение.

Этот внутренний документ фиксирует, почему движок и редактор используют
CSS/JS-обёртки для панорам, хотя обычные изображения удобнее хранить напрямую.
Он нужен для будущего пересмотра решения без повторного исследования уже
проверенных ограничений браузера.

## Исходные требования

Обёртка нужна не из-за формата эквидистантной панорамы и не является требованием
Three.js. Причина — обязательный автономный запуск новеллы двойным кликом через
`file://`, без локального HTTP-сервера.

Решение должно одновременно обеспечивать:

1. автоматическую загрузку панорамы после F5 без повторного выбора файла;
2. передачу изображения в WebGL, а не только отображение в `<img>`;
3. работу без локального сервера на настольных и мобильных устройствах;
4. безопасную обработку пакетов, полученных от пользователей;
5. освобождение временных данных и старых GPU-текстур при переходах.

## Почему прямое изображение оказалось ненадёжным

Обычное локальное изображение браузер иногда может показать в `<img>` или как
2D-фон, не предоставляя странице доступ к его пикселям. Для панорамы этого
недостаточно: Three.js передаёт изображение в WebGL через `texImage2D` или
`texSubImage2D`. WebGL запрещает загружать в текстуру изображение другого origin
и требует `SecurityError`, поскольку шейдеры позволяют косвенно читать текстуру.
Это закреплено в разделе [Origin Restrictions спецификации WebGL](https://registry.khronos.org/webgl/specs/latest/1.0/#origin-restrictions).

При `file://` локальная HTML-страница и соседнее изображение могут получить
несовместимые или непрозрачные origin в зависимости от браузера. В проекте это
проявлялось фактической ошибкой Chromium:

```text
SecurityError: Failed to execute 'texSubImage2D':
The image element contains cross-origin data, and may not be loaded.
```

Под HTTP эта проблема обычно решается одинаковым origin либо CORS-заголовком от
сервера. В автономном `file://` сервера нет, поэтому некому вернуть разрешающий
CORS-заголовок. Service Worker также не является заменой локальному серверу:
его регистрация ограничена безопасным контекстом, а целевой локальный запуск
проекта через `file://` этого механизма не предоставляет.

## Почему другие очевидные варианты не решили задачу

Ручной выбор изображения через `<input type="file">` технически работает:
браузер выдаёт странице разрешённый `File`, из него можно создать Blob URL и
WebGL-текстуру. Но такое разрешение не является обычным сохраняемым путём
проекта: после F5 файл нужно выбирать заново. Модель File API исходит из того,
что читаемые файлы сначала явно выбраны пользователем; см.
[Security and Privacy Considerations File API](https://www.w3.org/TR/FileAPI/#security-discussion).
Для движка и редактора требовалась автоматическая загрузка пути из сценария,
поэтому ручной выбор не решал задачу. Поле выбора и drag-and-drop исходного
изображения удалены из редактора: временное превью путало с поддерживаемым
ресурсом. Исходный растр теперь открывается только в конвертере, который создаёт
CSS-пакет для редактора.

JSON сам по себе также не предоставляет отдельного безопасного механизма
локальной загрузки. Для внешнего `.json` понадобился бы `fetch`/XHR, который
наследует ограничения origin в `file://`. Если же JSON подключить как исполняемый
`script`, это снова станет JS-обёрткой с теми же рисками выполнения кода.

Сравнение вариантов для текущих требований:

| Источник | Автоматически после F5 | Работает как WebGL-текстура под `file://` | Основное ограничение |
|---|---:|---:|---|
| Прямой `.jpg/.webp/.png` по пути | Да | Ненадёжно, в целевых проверках был `SecurityError` | Origin/CORS |
| Файл через `<input type="file">` | Нет | Да | Не предлагается редактором; используется только конвертером |
| Внешний JSON | Ненадёжно | Только после дополнительного декодирования | Нет подходящего локального загрузчика без `fetch`/исполнения |
| `*-360.js` | Да | Да | Выполняет произвольный код; хранит data URL в глобальной карте |
| `*-360.css` | Да | Да | Безопаснее JS, но остаётся нагрузка на CSS-парсер |

## Исторический JS-формат

JS-пакет был выбран потому, что локальный `<script src="...">` загружался после
F5 и мог зарегистрировать data URL изображения в
`window.VN360_PACKS_VARIANTS`. Data URL уже можно было передать декодеру и WebGL.

Недостаток принципиальный: браузер исполняет весь файл, поэтому пользовательский
JS способен выполнить произвольный код. По этой причине `*-360.js` теперь
считается только доверенным legacy-фолбэком.

Функции безопасного разбора и доверенного выполнения JS сохранены в коде
редактора для возможного возврата совместимости, но управляющие элементы
закомментированы в HTML. Обычный интерфейс редактора не предлагает загрузку или
выполнение `*-360.js`; импортированный путь остаётся данными и направляет
пользователя к соответствующему CSS-пакету. Это ограничение редактора не удаляет
JS-фолбэк из движка.

## Действующий CSS-формат

CSS-пакет сохраняет тот же практический канал автоматической загрузки через
локальный `<link>`, но хранит base64 как строки custom properties. Движок сначала
пробует одноимённый `*-360.css` и только при его отсутствии или ошибке загружает
legacy `*-360.js`.

Обычный интерфейс редактора принимает для основной панорамы только путь
`*-360.css`. Растровые пути, файловый выбор и drag-and-drop отклоняются, чтобы
сохранённый проект и превью использовали один восстанавливаемый после F5 формат.

CSS читается в отдельном sandbox-iframe. Единственный корневой `link` разрешается
случайным CSP nonce; скрипты, `@import`, изображения, шрифты и сетевые запросы
блокируются. После проверки известных полей данные декодируются в Blob URL,
созданный уже самой страницей, поэтому WebGL получает допустимый источник. Стили
пакета не подключаются к документу редактора или новеллы.

CSS не считается абсолютно пассивным: большой или специально сложный файл
способен нагружать CSS-парсер и память. Поэтому дополнительно ограничиваются
число частей и размер, а схема, MIME, base64, magic bytes, заявленный размер и
разрешение изображения проверяются до использования.

## Размер файлов и память

Обе обёртки увеличивают размер файла из-за base64 примерно на треть и не
уменьшают память декодированной текстуры. После декодирования грубая оценка
памяти RGBA-текстуры — `ширина × высота × 4` байта независимо от JPEG/WebP и
обёртки.

В CSS-пути временный iframe и Blob URL удаляются после декодирования, а Blob
очищается из состояния загрузчика. При смене панорамы старая WebGL-текстура
освобождается. Legacy JS сохраняет зарегистрированный data URL в глобальной
карте до перезагрузки страницы, поэтому на длинной новелле он хуже и по памяти.

## Условия пересмотра решения

От обёрток можно отказаться, если новое решение одновременно выполняет все
исходные требования этого документа. Перед заменой нужно отдельно повторить
проверку прямого изображения через `file://` в Chromium и WebKit, проверить
редактор и движок после F5, переходы между несколькими большими панорамами и
JS-фолбэк.

Прямые изображения можно рассмотреть заново, если приложение перейдёт на
HTTP(S), нативный контейнер с безопасным собственным протоколом либо появится
кроссбраузерный постоянный доступ к выбранной пользователем папке.

## Связанные компоненты

- `engine/engine.js` — загрузка пакетов и создание WebGL-текстур;
- `engine/story-sandbox-loader.js` — изолированная загрузка корневого
  `story360.js`; этот файл не загружает изображения `*-360.css`/`*-360.js`;
- `tools/scene360-editor.html` — загрузка панорам в редакторе;
- `tools/convert-360-img-to-css.html` — создание CSS/JS-пакетов;
- `docs/specs/spec-story.md` — пользовательский контракт форматов и порядок
  CSS-first/JS-fallback.

Корневой `story360.js` теперь выполняется в отдельном Worker и передаёт основной
странице только проверенную JSON-подобную карту. Это не меняет описанный выше
порядок загрузки самих изображений: legacy `*-360.js` по-прежнему является
отдельным исполняемым фолбэком после `*-360.css`.
