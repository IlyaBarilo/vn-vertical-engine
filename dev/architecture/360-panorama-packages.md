# Автономная загрузка 360-панорам

Статус: действующее архитектурное решение.

Этот внутренний документ фиксирует, почему движок и редактор используют
CSS-обёртки для панорам, хотя обычные изображения удобнее хранить напрямую,
и почему исторические JS-пакеты больше не загружаются.
Он нужен для будущего пересмотра решения без повторного исследования уже
проверенных ограничений браузера.

## Исходные требования

Обёртка нужна не из-за формата эквидистантной панорамы и не является требованием
Three.js. Причина — обязательный автономный запуск новеллы двойным кликом через
`file://`, без локального HTTP-сервера.

Решение должно одновременно обеспечивать:

1. автоматическую загрузку панорамы после F5 без повторного выбора файла;
2. передачу изображения в WebGL, а не только отображение в `<img>`;
3. работу без локального сервера на настольных и мобильных устройствах;
4. безопасную обработку пакетов, полученных от пользователей;
5. освобождение временных данных и старых GPU-текстур при переходах.

## Почему прямое изображение оказалось ненадёжным

Обычное локальное изображение браузер иногда может показать в `<img>` или как
2D-фон, не предоставляя странице доступ к его пикселям. Для панорамы этого
недостаточно: Three.js передаёт изображение в WebGL через `texImage2D` или
`texSubImage2D`. WebGL запрещает загружать в текстуру изображение другого origin
и требует `SecurityError`, поскольку шейдеры позволяют косвенно читать текстуру.
Это закреплено в разделе [Origin Restrictions спецификации WebGL](https://registry.khronos.org/webgl/specs/latest/1.0/#origin-restrictions).

При `file://` локальная HTML-страница и соседнее изображение могут получить
несовместимые или непрозрачные origin в зависимости от браузера. В проекте это
проявлялось фактической ошибкой Chromium:

```text
SecurityError: Failed to execute 'texSubImage2D':
The image element contains cross-origin data, and may not be loaded.
```

Под HTTP эта проблема обычно решается одинаковым origin либо CORS-заголовком от
сервера. В автономном `file://` сервера нет, поэтому некому вернуть разрешающий
CORS-заголовок. Service Worker также не является заменой локальному серверу:
его регистрация ограничена безопасным контекстом, а целевой локальный запуск
проекта через `file://` этого механизма не предоставляет.

## Почему другие очевидные варианты не решили задачу

Ручной выбор изображения через `<input type="file">` технически работает:
браузер выдаёт странице разрешённый `File`, из него можно создать Blob URL и
WebGL-текстуру. Но такое разрешение не является обычным сохраняемым путём
проекта: после F5 файл нужно выбирать заново. Модель File API исходит из того,
что читаемые файлы сначала явно выбраны пользователем; см.
[Security and Privacy Considerations File API](https://www.w3.org/TR/FileAPI/#security-discussion).
Для движка и редактора требовалась автоматическая загрузка пути из сценария,
поэтому ручной выбор не решал задачу. Поле выбора и drag-and-drop исходного
изображения удалены из редактора: временное превью путало с поддерживаемым
ресурсом. Исходный растр теперь открывается только в конвертере, который создаёт
CSS-пакет для редактора.

JSON сам по себе также не предоставляет отдельного безопасного механизма
локальной загрузки. Для внешнего `.json` понадобился бы `fetch`/XHR, который
наследует ограничения origin в `file://`. Если же JSON подключить как исполняемый
`script`, это снова станет JS-обёрткой с теми же рисками выполнения кода.

Сравнение вариантов для текущих требований:

| Источник | Автоматически после F5 | Работает как WebGL-текстура под `file://` | Основное ограничение |
|---|---:|---:|---|
| Прямой `.jpg/.webp/.png` по пути | Да | Ненадёжно, в целевых проверках был `SecurityError` | Origin/CORS |
| Файл через `<input type="file">` | Нет | Да | Не предлагается редактором; используется только конвертером |
| Внешний JSON | Ненадёжно | Только после дополнительного декодирования | Нет подходящего локального загрузчика без `fetch`/исполнения |
| `*-360.js` | Технически да | Да | Запрещён: выполняет произвольный код |
| `*-360.css` | Да | Да | Безопаснее JS, но остаётся нагрузка большого Base64 на память |

## Исторический JS-формат

JS-пакет ранее использовался потому, что локальный `<script src="...">` загружался после
F5 и мог зарегистрировать data URL изображения в
`window.VN360_PACKS_VARIANTS`. Data URL уже можно было передать декодеру и WebGL.

Недостаток принципиальный: браузер исполняет весь файл, поэтому пользовательский
JS способен выполнить произвольный код. Движок теперь отвергает все варианты
пути `*-360.js`, включая normal, mobile и произвольные суффиксы, не создаёт для
них `<script>` и не читает прежние глобальные карты `VN360_PACKS*`.

Конвертер может пассивно прочитать data URL из старого пакета, созданного этим
же инструментом, чтобы перенести изображение в CSS. Содержимое импортированного
файла при этом не выполняется. Новый JS-пакет конвертер не создаёт. Это канал
миграции данных, а не совместимый runtime-формат.

## Действующий CSS-формат

CSS-пакет сохраняет практический канал автоматической загрузки локального файла,
но хранит base64 как строки custom properties. Для панорамных
изображений движок принимает только `*-360.css`; при отсутствии или ошибке CSS
панорама не загружается и JS-фолбэк не выполняется.

Путь пакета подчиняется общей политике авторских ресурсов: только канонический
относительный `assets/...` с прямыми слешами, без URL, абсолютного пути,
traversal, query/hash и percent-encoding. Это проверяется при разборе сценария и
повторно перед созданием URL в runtime; выбор варианта качества выполняется уже
после проверки базового пути.

Обычный интерфейс редактора принимает для основной панорамы только путь
`*-360.css`. Растровые пути, файловый выбор и drag-and-drop отклоняются, чтобы
сохранённый проект и превью использовали один восстанавливаемый после F5 формат.

Основной путь открывает CSS в отдельном sandbox-iframe как верхнеуровневый
текстовый документ `text/css`, а не подключает его как таблицу стилей. Поэтому
браузер не применяет правила пакета и не выполняет `@import` или загрузку других
ресурсов. Родительская страница читает текст документа того же origin, после чего
строгий парсер допускает только комментарии и одно правило `#vn360-pack` с
известными двойными строковыми свойствами. Импорты, дополнительные правила,
CSS-escape, дубли свойств, пропущенные и лишние части отклоняются до декодирования.

Доступ Firefox к текстовому пути для соседних `file://`-файлов зависит от политики
локальных origin: при `security.fileuri.strict_origin_policy = true` чтение может
быть запрещено. Chromium и Microsoft Edge также назначают локальному CSS закрытый
origin и не дают родительской странице прочитать его текст. Только для такого
отказа под `file://` используется совместимый второй sandbox-iframe:
единственный корневой `<link>` разрешён
случайным CSP nonce, а `@import`, скрипты, изображения, шрифты, сеть и остальные
побочные ресурсы запрещены CSP. Из iframe читаются только известные custom
properties, после чего работают те же проверки метаданных и бинарного содержимого.
При HTTP(S), ошибке формата или ошибке строгого парсера этот запасной путь не
включается. Такое разделение учитывает различия локальных origin и поддержки CSP
nonce, сохраняя реальный `file://` в Firefox и Edge.

Iframe совместимого CSS-пути остаётся в layout за пределами экрана с размером
1×1, `visibility:hidden`, `pointer-events:none`, `tabIndex = -1` и `aria-hidden`.
Его нельзя скрывать через `hidden`/`display:none`: Firefox в таком iframe
возвращает пустые custom properties через `getComputedStyle()`, и корректный пакет
ошибочно отклоняется по `--vn360-schema`. Текстовый iframe по-прежнему использует
`hidden`, поскольку вычисление стилей ему не требуется. Sandbox, CSP, nonce и
удаление обоих временных iframe после завершения загрузки сохраняются.
Регрессионная проверка включает строгую политику Firefox явно; в Playwright Test
её задают через `use.launchOptions.firefoxUserPrefs`, а при прямом `launch()` —
через `firefoxUserPrefs`. Это особенно важно для канала `moz-firefox`, где настройки
автоматизации по умолчанию ослабляют доступ к локальным файлам.

После проверки известных полей данные декодируются в Blob URL, созданный уже
самой страницей, поэтому WebGL получает допустимый источник. Большой файл всё
равно способен нагружать память, поэтому отдельно ограничиваются Base64, число и
размер частей, а также схема, MIME, magic bytes, заявленный размер и разрешение
изображения. На основном текстовом пути runtime дополнительно отклоняет исходный
CSS больше 130 МиБ. В совместимом `file://` пути браузер загружает
таблицу до передачи управления JavaScript, поэтому runtime не может надёжно
измерить весь исходник; границу 130 МиБ до запуска обеспечивают конвертер и
аудитор студенческого проекта. Фактические размеры
PNG/JPEG/WebP читаются из бинарного заголовка до создания Blob URL и запуска
браузерного декодера; значения должны совпасть с метаданными CSS-пакета.

## Размер файлов и память

CSS-обёртка увеличивает размер файла из-за base64 примерно на треть и не
уменьшает память декодированной текстуры. После декодирования грубая оценка
памяти RGBA-текстуры — `ширина × высота × 4` байта независимо от JPEG/WebP и
обёртки.

Для normal и mobile действует единый предохранительный предел: не более
`20000 × 15000` и не более `300 000 000` пикселей. Это граница от заведомо
вредных размеров, а не обещание работы такого кадра на любом устройстве:
проверка `MAX_TEXTURE_SIZE` текущего WebGL остаётся обязательной, а кадр на
верхней границе требует около 1,12 ГиБ только для одного RGBA-буфера. Сжатие
уменьшает CSS-файл, но не эту память.

Исходный CSS ограничен 130 МиБ, Base64 — 128 МиБ, бинарное изображение — 96 МиБ,
пакет — 4096 частями по 32 КиБ. JPEG обязан содержать SOF с размерами в первых
4 МиБ заголовка; PNG и WebP хранят размеры в своих начальных обязательных
структурах. Лимиты данных одинаковы в движке, редакторе и конвертере; размер
всего файла дополнительно проверяет аудитор проекта.

В CSS-пути временный iframe и Blob URL удаляются после декодирования, а Blob
очищается из состояния загрузчика. Этим lifecycle и фоновой очередью владеет
`engine/panorama-package-controller.js`; при окончательном `pagehide` контроллер
дополнительно отменяет свои таймеры и HEAD-запросы, удаляет незавершённые iframe
и отзывает все ещё выданные Blob URL. `engine.js` получает от контроллера только
проверенный временный ресурс и малый снимок статистики. При смене панорамы
`engine.js` освобождает старую WebGL-текстуру. Старые JS-пакеты регистрировали
data URL в глобальной карте до перезагрузки страницы; удаление этой ветки также
устранило лишнее долгоживущее состояние.

Текстовая статистика использует тот же строгий загрузчик и после первого
открытия полностью проверяет все семантически объявленные CSS-панорамы выбранного
normal/mobile-качества ограниченным пулом: до четырёх пакетов одновременно на
компьютере и до двух на уверенно определённом телефоне. Очередь не зависит от
видимости панели и продолжается после её закрытия. На время видимого графа
ресурсов или незавершённой загрузки текущей WebGL-панорамы новые задания очереди
уступают им приоритет; уже начатые завершаются. После каждого пакета Blob URL и
декодированное изображение освобождаются; сессионный кеш до F5 хранит только
статус, путь, места использования и малые метаданные. Полноразмерные изображения
графа в этот кеш не помещаются и при повторном построении графа загружаются
заново, но успешное декодирование графом или runtime засчитывается как результат
проверки.

## Условия пересмотра решения

От обёрток можно отказаться, если новое решение одновременно выполняет все
исходные требования этого документа. Перед заменой нужно отдельно повторить
проверку прямого изображения через `file://` в Chromium, Firefox и WebKit, проверить
редактор и движок после F5, переходы между несколькими большими панорамами,
обработку отсутствующего CSS и гарантированный отказ от выполнения JS-пакета.

Прямые изображения можно рассмотреть заново, если приложение перейдёт на
HTTP(S), нативный контейнер с безопасным собственным протоколом либо появится
кроссбраузерный постоянный доступ к выбранной пользователем папке.

## Связанные компоненты

- `engine/panorama-package-controller.js` — строгий разбор и изолированная
  загрузка CSS-пакетов, Blob URL и фоновая очередь полной проверки;
- `engine/engine.js` — выбор панорамного действия, декодирование выданного
  ресурса в WebGL-текстуру, renderer, управление камерой и UI статистики;
- `engine/resource-path-policy.js` — единая проверка путей `assets/...` и
  допустимых типов ресурсов перед загрузкой;
- `engine/story-sandbox-loader.js` — изолированная загрузка корневого
  `story360.js`; этот файл не загружает изображения `*-360.css`/`*-360.js`;
- `tools/scene360-editor.html` — загрузка панорам в редакторе;
- `tools/convert-360-img-to-css.html` — создание CSS-пакетов и пассивная миграция
  данных из старых JS-пакетов;
- `docs/specs/spec-story.md` — пользовательский контракт CSS-формата.

Корневой `story360.js` — отдельный файл данных сцен: он выполняется в Worker и
передаёт основной странице только проверенную JSON-подобную карту. Он не является
пакетом изображения. Файлы изображений `*-360.js` движок всегда отвергает;
поддерживаемый автономный формат панорамного изображения — только `*-360.css`.

Версии двух 360°-форматов независимы. Корневая карта обязана содержать числовое
поле `version: 1`; Worker проверяет его до глубокого копирования и отклоняет
отсутствующую или неизвестную версию. CSS-пакет изображения отдельно объявляет
строковую схему `vn360-css-pack-v1`, которую проверяют runtime и редактор.
Ни одна из этих версий не записывается в `story.js` и не меняется автоматически
вместе с номером релиза движка.

Проверка и построение безопасной копии `window.STORY360` выполняются внутри Worker
до вызова `MessagePort.postMessage`, поэтому исходный пользовательский объект не
попадает в structured clone и память основного окна. Ограничение в 250 000 узлов
учитывает контейнеры и каждое примитивное значение, в том числе элементы массивов;
длина массива сверяется с оставшейся квотой до выделения массива-копии. Дополнительно
действуют предел глубины 64, предел одной строки 4 МиБ и суммарный предел строк
16 МиБ. Валидатор использует встроенные функции, сохранённые до запуска файла,
поэтому `story360.js` не может ослабить эти проверки их подменой.
Если structured clone восстанавливает обычные прототипы объектов, основная страница
заменяет их на нулевые на месте, не создавая ещё одну глубокую копию карты.

Сам исполняемый формат `story360.js` всё ещё позволяет создать большой объект внутри
изолированного Worker до начала проверки. Таймаут завершает зависший Worker, а ранняя
валидация не даёт продублировать такой объект в основном окне, но полностью исключить
исходное выделение памяти можно только переходом на декларативный неисполняемый формат.
